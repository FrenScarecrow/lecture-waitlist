# 产品简报：讲座报名与候补系统

## 执行摘要

讲座报名与候补系统是一个单机部署、电脑浏览器使用的 Web 应用，用来替代研究生学院现在靠微信群接龙 / 问卷组织的讲座报名。学生在页面上报名讲座；名额满了会提示满员，用户可自行选择加入候补，按加入时间获得顺序号；有人取消报名，系统**立即**按候补顺序把下一位补入，全程留痕、可审计。

表面看它是一个报名 CRUD 系统，骨子里是一个**并发正确性 + 候补状态机**的问题：最后一个名额在报名、取消、补位同时发生时只能被一个人占用；同一空位不能补给两个人；补位动作被重复触发也必须幂等。把这三件事**保证**下来，才是这个产品区别于问卷 / 接龙的根本。

系统面向学生与管理员（助教 / 组织者）两类角色，真实规模是每场几十到几百人。本期只覆盖报名、候补自动补位、容量调整与审计三块核心能力；不做支付，不做邮件 / 短信 / 微信等外部推送。

## 问题

学院每周有学术报告、组会、党课等讲座，报名目前靠微信群接龙或问卷：

- 名额满了没有正式的候补机制，有人取消后靠人工通知候补者；
- 人工通知经常漏通知、乱序、重复通知；
- 管理员要手工核对人数、导出名单，补位过程无记录、不可审计。

结果是：热门讲座名额被浪费（有人取消、候补没补上），候补顺序说不清产生纠纷，管理员陷在琐碎的手工劳动里。

## 方案

一个 Web 应用，三条核心闭环：

1. **发布与报名** — 管理员发布讲座（标题、开始时间、容量等字段）；报名截止由系统根据开始时间自动派生（开始前 30 分钟）。学生报名并实时看到剩余名额；报名受容量约束，并发下不超卖、不双占。
2. **候补与自动补位** — 名额满时，报名请求返回满员提示，由用户**自行选择**是否加入候补；加入后按「加入候补的时间」获得顺序号，不加入则不参与补位。有人取消报名，系统**立即**按候补顺序把下一位直接标记为「已报名」并生成站内通知（仅告知，无需确认）；报名截止前可主动退出；截止时系统清空整个队列并发出站内通知。
3. **运营与审计** — 管理员可调整容量（扩容即时生效；缩容将超出部分的后报名者移除，并放在候补队列的最前面）、导出报名名单；发布、取消、补位、容量调整等关键操作全程记日志，补位顺序可追溯审计。

## 为什么值得做

1. **候补语义的正确性与可审计性**：不超卖、不双占、按加入顺序补位、幂等，事后可查证——这是接龙和问卷做不到的。
2. **场景适配**：单机部署、零外部依赖，匹配「管理员是不懂运维的学生助教」这个现实约束。

## 谁在用

- **学生（报名者）**：报名讲座、看剩余名额、满了可选择加入候补，并在有空位时被公平、可靠地补入。
- **候补学生**：主动加入候补后排在队列里，关心顺序公平——先加入候补的先补入，且可查证。
- **管理员（组织者 / 助教）**：发布讲座、管理容量、导出名单，希望发布一场讲座不超过 5 步，补位自动、无需手工通知。

## 成功标准

**功能 / 产品**

- 任一时刻有效报名数不超过讲座容量。
- 管理员发布一场讲座不超过 5 步。
- 取消事务提交即完成补位。
- 报名截止后 1 分钟内完成候补清空并通知。
- **验收边界**：满员时未加入候补的用户，后续容量扩容不会被自动补入，需重新报名。

**两条非功能要求（NFR）**

1. **并发正确性**：并发报名 / 取消 / 补位同时发生时，最后一个名额只被一个请求占用；不超卖、不双占。
2. **补位正确性**：取消报名后按候补加入顺序直接补位，同一空位只补给一人；重复触发不产生二次补位；全程可审计。

## 范围

**本期做**（三个能力域）

- **发布与报名**：发布讲座、列表与实时余量、并发报名、截止前取消。
- **候补与自动补位**：满员提示与主动加入候补（分配顺序号）、取消触发直接补位、补位幂等与重复触发防护、候补者主动退出候补、报名截止清空候补、候补顺序审计。
- **运营与治理**：容量调整、报名名单导出、关键操作日志。

**明确不做**

- 支付。
- 邮件 / 短信 / 微信等外部推送（通知仅站内，不配置 SMTP、不依赖外部服务）。
- 多校区、多租户。
- 复杂权限体系（仅学生、管理员两种角色）。
- 院系配额、名额转让。

## 愿景

如果本期站得住，它可以从「一个课程作业」长成学院真正日常使用的报名工具：各类讲座统一报名，候补公平有据可查，管理员不再做手工接龙和通知。再往后，可扩展多场讲座冲突检测、学生个人日程、面向更多院系的复用——但那是 2–3 年后的事。本期只做这一件小事，并把它做对。
