# PRD：讲座报名与候补系统 (lecture-waitlist)

## 0. 文档目的

本文档是「讲座报名与候补系统」的产品需求说明（PRD），面向实现本系统的开发团队与《软件项目管理》课程评审，用于把产品简报里已敲定的范围翻译成可测试、可追溯的功能需求与验收口径。它建立在已定稿的《产品简报》之上（`_bmad-output/planning-artifacts/briefs/brief-lecture-waitlist-2026-11-22/`），简报中已否决与演进的方案沉淀在对应 addendum.md，本文档不重复，只在需要时引用。

结构：§3 术语表是全文唯一词汇来源（FR、UJ、SM 一律使用表中术语，不引入同义词）；§4 按特性分组、功能需求全局编号（FR-1…FR-N）；§5 承载跨特性的非功能需求（并发正确性、补位正确性等本产品的核心）；文中推断而未确认之处以 `[ASSUMPTION]` 内联标注并在 §10 汇总。

## 1. 愿景

研究生学院每周都有学术报告、组会、党课等讲座，报名目前靠微信群接龙或问卷：名额满了没有正式候补，有人取消靠人工通知，漏通知、乱序、重复通知是常态，管理员陷在手工核对名单与无据可查的补位纠纷里。

本系统用一个单机部署、电脑浏览器访问的 Web 应用替代这套人工流程：学生在页面报名讲座并实时看到余量，满员时自行选择是否加入候补；有人取消，系统立即按候补顺序把下一位自动补入并站内告知；容量调整、名单导出、关键操作全程留痕可审计。

表面是报名 CRUD，本质是一道**并发正确性 + 候补状态机**的题：最后一个名额在报名、取消、补位同时发生时只能被一人占用；同一空位不能补给两人；补位被重复触发也必须幂等。把这三件事**保证**下来，才是它区别于接龙与问卷的根本。

## 2. 目标用户

### 2.1 待完成的工作（JTBD）

- **学生（报名者）**：报名讲座、实时看到剩余名额；满了能自己决定要不要排候补，并且放心——一旦排上，先来后到、公平可查。
- **候补学生**：主动加入候补后排在队列里，关心顺序公平与可查证：先加入的先补入，且能查到自己为什么排在这个位置。
- **管理员（助教 / 组织者）**：发布讲座、调容量、导名单，希望发布一场讲座不超过 5 步，补位自动、无需手工通知，且补位顺序事后能说清楚。

### 2.2 关键用户旅程

- **UJ-1. 助教小王发布一场讲座。**
  - **人物与情境**：小王是负责本场学术报告的学生助教，不懂运维，只想快点把报名发出去。
  - **入口状态**：已用管理员账号登录，进入管理页。
  - **路径**：点「发布讲座」→ 填标题、开始时间、结束时间、容量、报名开始时间、报名截止（可选地点 / 主讲人 / 类型）→ 提交。系统校验字段、生成状态为「已发布」的讲座。
  - **高潮**：提交后即出现在学生端列表，小王确认「报名已开放」。
  - **收尾**：讲座进入「已发布」，可继续发布下一场或查看名单。
  - **边界**：若容量填 0 或报名截止晚于开始时间，系统拒绝提交并提示改哪个字段。

- **UJ-2. 学生张三报名，满员时选择加入候补。**
  - **人物与情境**：张三用学号登录，想报名一场还剩 1 个名额的热门党课。
  - **入口状态**：已登录学生账号，在讲座列表页。
  - **路径**：看到目标讲座与「剩余 1 人」→ 点「报名」→ 系统提示报名成功。另一场满员的讲座显示「已满」，点进去提示满员并可「加入候补」。
  - **高潮**：张三对满员那场点「加入候补」，系统返回他的候补顺序号（如第 3 位）。
  - **收尾**：张三能看到自己的报名与候补状态；有空位时会被自动补入并收到站内通知。
  - **边界**：若报名尚未开始，讲座显示「报名未开始」、无法报名；若同一学号重复报名同一场，系统拒绝（不双占）。

- **UJ-3. 候补者李四被自动补入。**
  - **人物与情境**：李四排在某讲座候补第 1 位，正等一个空位。
  - **入口状态**：已有报名者取消，产生一个空位。
  - **路径**：系统在取消事务内锁定空位 → 按候补顺序取第 1 位李四 → 将李四状态转为「已报名」→ 生成站内通知（仅告知，无需确认）。
  - **高潮**：李四下次打开页面，看到未读通知「您已补位成功」，且报名状态变为已报名。
  - **收尾**：李四的候补记录被消费，队列前移；整个过程留痕可审计。

- **UJ-4. 助教小王调整容量。**
  - **人物与情境**：讲座临时换到更大的教室，小王要把容量从 50 调到 80。
  - **入口状态**：管理员登录，打开某场「已发布」讲座的管理页。
  - **路径**：改容量为 80 → 提交。系统即时生效：按候补顺序把最多 30 位候补者自动补入。
  - **高潮**：候补者批量转为已报名并收到通知，小王看到报名数上涨、候补缩短。
  - **收尾**：若反向缩容，超出部分按「后报名者先移出」转入候补队首。全程留日志。

## 3. 术语表

下游实现与评审必须严格使用以下术语，不得在 FR / UJ / SM 中另起同义词。

- **讲座（Lecture）** — 一场活动。字段：标题、开始时间、结束时间、容量、报名开始时间、报名截止、状态，可选地点、主讲人、类型。
- **讲座状态（Lecture status）** — 讲座的生命周期状态：`已发布`（发布后、开始前）、`已开始`（开始时间起）、`已结束`（结束时间起）。由系统按时间自动流转；报名相关规则以此状态 + 时间边界判断。
- **报名（Registration）** — 学生占用一个名额的动作及其结果；已报名即占用一个名额。
- **容量（Capacity）** — 一场讲座可容纳的报名人数上限。
- **满员（Full）** — 有效报名数已达到容量。
- **候补（Waitlist）** — 满员后学生主动加入的等待队列，按「加入候补时间」排序。
- **候补者（Waitlisted user）** — 已加入候补的学生。
- **顺序号（Sequence number）** — 候补者在候补队列中的位置，按加入候补时间分配，对学生可见。
- **补位（Promotion）** — 出现空位时，按候补顺序把下一位候补者状态转为「已报名」的动作。
- **扩容 / 缩容（Capacity increase / decrease）** — 管理员调整容量：扩容释放空位并触发补位；缩容把超出部分按「后报名者先移出」转入候补。
- **后报名者先移出（Last-in-first-out）** — 缩容时确定移出顺序的规则：报名越晚越先被移入候补。
- **报名开始时间（Registration open time）** — 报名开放的起始时刻；可为空，为空表示发布即开放。讲座发布后、报名开始前，讲座可见但不可报名。
- **报名窗口（Registration window）** — 报名 / 加入候补 / 取消报名的有效时间段，即 [报名开始时间, 报名截止时间]。
- **报名截止（Registration deadline）** — 报名窗口的结束时刻；到点系统自动清空候补。
- **站内通知（In-app notification）** — 补位、被移出候补、候补自动清空等事件生成的消息，仅站内展示（通知页 + 未读标记），不依赖任何外部推送。
- **学生 / 管理员（Student / Admin）** — 两类角色；学生账号即学号，管理员即助教本人。

## 4. 功能

### 4.1 身份与访问

**描述：** 学生与管理员都通过账号密码登录；不提供自助注册，账号由管理员（或直接写库）创建。学生账号用户名即学号，管理员账号为助教专用。账号初始密码由管理员创建账号时设定，无自助找回 / 重置。登录后按角色进入学生端或管理端。

**功能需求：**

#### FR-1：账号密码登录

学生与管理员使用用户名 + 密码登录系统；学生用户名即学号。登录成功建立会话，失败给出统一错误提示（不泄露"账号不存在"与"密码错误"的差别）。

**可测试后果：**
- 用正确学号 + 密码登录成功，进入学生端；错误密码被拒绝。
- 管理员账号登录进入管理端；学生账号无法访问管理端。
- 未登录访问受保护页面被重定向到登录页。

#### FR-2：两类角色

系统仅区分「学生」「管理员」两种角色，无更细的权限分级；管理员即助教本人，单人直接生效，无审批流、无多人协作。

**可测试后果：**
- 学生可报名 / 加入候补 / 取消报名 / 退出候补 / 查看通知与自己的状态。
- 管理员可发布讲座 / 调整容量 / 导出名单 / 查看操作日志。
- 学生访问任何管理操作返回无权限。

### 4.2 讲座发布与报名

**描述：** 管理员发布讲座；学生在列表实时看到余量并报名，报名受容量与报名窗口（报名开始时间 → 报名截止）约束，并发下不超卖、不双占。报名窗口外（报名开始前、报名截止后）或讲座已开始 / 已结束后，报名、加入候补、取消报名全部关闭。实现 UJ-1、UJ-2。

**功能需求：**

#### FR-3：发布讲座

管理员可发布一场讲座，填写标题、开始时间、结束时间、容量、报名开始时间、报名截止，可选地点、主讲人、类型；发布后状态为「已发布」，学生端立即可见。`[ASSUMPTION: 报名开始时间为空时缺省为发布即开放报名。]`

**可测试后果：**
- 必填项缺失或非法（容量 ≤ 0、报名开始时间 ≥ 报名截止、报名截止晚于开始时间）时拒绝提交并提示具体字段。
- 提交成功后讲座出现在学生端列表，状态为「已发布」。
- 发布一场讲座的操作步骤 ≤ 5 步（成功标准 SM-4）。

#### FR-4：浏览列表与实时余量

学生登录后可浏览未结束讲座列表，实时看到每场的剩余名额、满员 / 已满标记与状态。

**可测试后果：**
- 列表显示每场讲座的「剩余 N 人」；N=0 时显示「已满」。
- 报名未开始（当前时间早于报名开始时间）的讲座，显示「报名未开始 / X 点开放」且不可报名。
- 报名数变化后，余量在页面刷新 / 下次读取时反映最新值。
- 已结束讲座不进入报名列表（或明确标记为已结束、不可报名）。

#### FR-5：报名讲座

学生可对「已发布」且处于报名窗口内（当前时间 ∈ [报名开始时间, 报名截止]）的讲座报名：有空位则立即报名成功并占用名额；满员则提示满员（不可直接报名）。同一学号对同一场讲座只能报名一次（不双占）。报名在并发下不超卖。实现 UJ-2。

**可测试后果：**
- 有空位时报名成功，报名数 +1；达到容量后新报名被拒绝并提示满员。
- 同一学号重复报名同一场被拒绝。
- 并发下（多个请求同时抢最后一个名额）至多一人成功，报名数绝不超过容量（NFR-1）。
- 报名开始前、报名截止后，或讲座已开始 / 已结束后，报名请求被拒绝。

#### FR-6：取消报名

学生在报名窗口内可取消自己已报名的讲座；取消后释放名额并触发补位（见 FR-8）。

**可测试后果：**
- 报名窗口内取消成功，报名数 -1，该名额进入补位流程。
- 报名窗口外（报名开始前、报名截止后）或讲座已开始 / 已结束后，取消被拒绝。

### 4.3 候补与自动补位

**描述：** 满员时学生主动选择加入候补并获顺序号；有人取消（或管理员扩容）即按候补顺序自动补位，补位幂等、不二次补位，顺序全程可审计。所有候补相关事件（补位成功、被移出候补、候补自动清空）生成站内通知，学生在通知页查看、带未读标记。实现 UJ-2、UJ-3。

**功能需求：**

#### FR-7：满员提示与主动加入候补

学生报名满员讲座时，系统提示满员，并由学生**主动选择**是否加入候补；加入后按加入候补时间分配顺序号（对学生可见）。不加入则不参与补位。实现 UJ-2。

**可测试后果：**
- 满员讲座报名被拒后，显示「加入候补」选项，学生确认后进入候补并拿到顺序号。
- 顺序号按加入候补时间递增；同一学生不重复加入候补。
- 报名窗口外（报名开始前 / 截止后）不可加入候补。
- 未加入候补者不在候补队列中，后续扩容 / 补位不涉及。

#### FR-8：取消触发直接补位

有报名者取消（FR-6）产生空位时，系统**立即**按候补顺序把下一位候补者状态转为「已报名」，并生成站内通知（仅告知，无需确认）。实现 UJ-3。

**可测试后果：**
- 取消事务提交即完成补位，补位者立即成为已报名，报名数不因空位而减少。
- 补位按候补顺序（先加入先补入）。
- 补位者收到站内通知；无候补者时取消仅释放名额、不补位。

#### FR-9：补位幂等与重复触发防护

同一空位只补给一位候补者；补位被重复触发（重复请求、并发取消多个名额、取消与扩容同时发生）时不产生二次补位、不双占。实现 NFR-2。

**可测试后果：**
- 对同一空位并发 / 重复触发补位，最终只有一位候补者被补入。
- 补位记录与日志一一对应，无重复补位条目。
- 多个名额同时释放时，按顺序一对一补位，不重不漏。

#### FR-10：退出候补

候补者可在报名截止前主动退出候补；到报名截止时刻，系统自动将所有仍在候补的候补者清空（标记为未入选、生成通知）。退出候补的最后时限为讲座开始前 30 分钟（T=30，系统常量、不可配置）；若报名截止早于该时刻，则以报名截止为准（截止即自动清空）。

**可测试后果：**
- 报名截止前，候补者主动退出候补成功，队列前移。
- 报名截止时刻，所有残留候补者被自动清空，并收到通知。
- 退出候补不产生空位、不触发补位。

#### FR-11：候补顺序审计

候补的加入时间、顺序号、补位 / 退出 / 清空记录全程留痕，任何时点的候补顺序都可追溯还原。

**可测试后果：**
- 给定一场讲座，能据日志还原任一时刻的候补顺序与顺序号。
- 每次补位 / 退出 / 清空都有对应日志条目（操作人、时间、顺序号、结果）。

### 4.4 运营与治理

**描述：** 管理员调整容量（扩容即时生效并补位、缩容按「后报名者先移出」转入候补）、导出名单、查看关键操作日志。管理员即助教本人，单人直接生效。实现 UJ-4。

**功能需求：**

#### FR-12：容量调整

管理员可在讲座发布后、讲座开始前 60 分钟之前调整容量（窗口为 [发布时间, 开始前 60 分钟]，之后关闭）：扩容即时生效并触发补位（按候补顺序补入直至满员或无候补者）；缩容将超出部分按「后报名者先移出」的顺序转入候补。缩容移出者整体排在现有候补队列之前、内部按原报名先后排序；缩容不产生空位、不触发补位。

**可测试后果：**
- 扩容后，按候补顺序把候补者补入，直至报名数 = min(新容量, 原报名数 + 候补数)。
- 扩容时，满员后未加入候补的用户**不会**被自动补入（验收边界 SM-5）。
- 缩容后报名数 = 新容量，被移出者进入候补队首、顺序为原报名先后。
- 缩容不触发补位。
- 讲座开始前 60 分钟后，或状态非「已发布」，容量调整请求被拒绝。

#### FR-13：报名名单导出

管理员可导出讲座报名名单为 CSV，使用 **UTF-8 with BOM** 编码，保证 Excel 直接打开不乱码；字段含学号、姓名、报名时间、候补顺序等。

**可测试后果：**
- 导出的 CSV 以 UTF-8 BOM 开头，Excel 直接打开中文无乱码。
- 名单字段含学号、姓名、报名时间（及候补顺序，若适用），与库内数据一致。

#### FR-14：关键操作日志

发布讲座、报名、取消、补位、加入 / 退出候补、容量调整、候补自动清空等关键操作全程记日志，补位顺序可追溯审计。

**可测试后果：**
- 每类关键操作均有日志条目（操作人、时间、讲座、动作、前后状态 / 顺序）。
- 管理员可查看日志，据此还原补位顺序与容量调整历史（支撑 NFR-2 的「可审计」）。

## 5. 跨特性非功能需求（NFR）

本节的两条正确性 NFR 是本产品的核心验收口径，优先级高于一切性能 / 便利优化。

- **NFR-1 并发正确性（不超卖、不双占）**：并发报名 / 取消 / 补位同时发生时，最后一个名额只被一个请求占用；任一时刻有效报名数不超过容量；同一学号同一讲座不双占。
- **NFR-2 补位正确性（按序、幂等、可审计）**：取消后按候补加入顺序直接补位，同一空位只补给一人；重复触发不二次补位；全程可审计。
- **NFR-3 补位时延**：取消事务提交即完成补位，P95 ≤ 1 秒。
- **NFR-4 部署与环境**：单机部署、零外部依赖（不配置 SMTP、不依赖短信 / 微信等外部服务），电脑浏览器访问；面向「不懂运维的学生助教」，部署与运行门槛要低。

## 6. 非目标（明确不做）

- **支付**：报名不涉及任何支付。
- **外部推送**：不做邮件 / 短信 / 微信推送，通知仅站内。
- **多校区 / 多租户**：单机、单院系场景。
- **复杂权限体系**：仅学生 / 管理员两种角色，无管理员分级、无审批流、无多人协作。
- **院系配额、名额转让**：无。
- **用户自助注册**：账号由管理员（或写库）创建，无开放注册。

## 7. MVP 范围

### 7.1 本期做

四个能力域（§4 全部 FR-1…FR-14）：身份与访问、讲座发布与报名、候补与自动补位、运营与治理。

### 7.2 本期不做（MVP 外）

- 支付、外部推送、多校区 / 多租户、复杂权限、院系配额 / 名额转让、自助注册（见 §6）。
- 多场讲座冲突检测、学生个人日程、面向更多院系的复用——2–3 年后演进方向，不在本期。

## 8. 成功指标

每条 SM 标注它验证的功能需求；反指标用于防止为追指标而牺牲正确性。

**主要**

- **SM-1**：任一时刻有效报名数 ≤ 容量，无超卖 / 双占（100% 保证）。验证 FR-5、NFR-1。
- **SM-2**：取消后按候补加入顺序补位、同一空位只补一人、重复触发不二次补位、全程可审计。验证 FR-8、FR-9、NFR-2。
- **SM-3**：取消事务提交即完成补位，P95 ≤ 1 秒。验证 FR-8、NFR-3。
- **SM-4**：管理员发布一场讲座 ≤ 5 步。验证 FR-3。
- **SM-5（验收边界）**：满员时未加入候补的用户，后续扩容不被自动补入。验证 FR-12。

**次要**

- **SM-6**：管理员一键导出 CSV（UTF-8 BOM），Excel 直接打开无乱码。验证 FR-13。

**反指标（不得为此优化）**

- **SM-C1**：报名 / 补位吞吐量——不得以放宽「不超卖 / 不双占 / 可审计」为代价追求吞吐（例如用无锁但可能双占的实现换吞吐）。
